# 00 · KVP (Apple) reproduction with Qwen2-1.5B: RLOO vs PPO

**Report section:** §4.2 "Starting point: reimplementing KVP".
**Code:** [`ml-learning-to-evict/`](../../ml-learning-to-evict/) (Apple's repo + our additions, see the provenance block in its README).

## Question

Can we run the full KVP pipeline (Learning to Evict from Key-Value Cache, Apple)
end-to-end with a small model (Qwen2-1.5B-Instruct instead of the paper's
Qwen2.5-7B-Instruct), and validate that the reproduction is correct? Also: does PPO
(with a value critic) work as an alternative to the paper's RLOO + Gumbel-top-k?

## Setup

| component | value |
|---|---|
| model | Qwen2-1.5B-Instruct (28 layers, 2 KV heads per layer = 56 agents) |
| dataset | RULER (synthetic retrieval, "4096" config, prompts truncated to 2048 tokens) |
| training | offline: Q/K/V activations are captured to disk, the agents never load the LLM |
| algorithms | RLOO + Gumbel-top-k (the paper's) and PPO with a critic (our addition) |
| reward | future attention (normalized AUC over budgets), the paper's |
| pipeline | `run_experiment.sh`: data-gen (`preprocess_qwen1b.yaml`) → train (`train_qwen1b*.yaml`) → eval (`scripts/eval_vs_baseline.py`) |

Important adaptation details (all via config, without touching Apple's code):
- The agent keeps `head_dim=128` (identical to the 7B), so the agent architecture is unchanged.
- Qwen2-1.5B has 2 KV heads per layer (GQA, groups of 6 queries), 56 agents in total.
- The 1-line fix in `kvsorting_env.py` (the eval dataloader was not reset between evals,
  upstream assigned a dead attribute) is marked with a `local fix` comment.
- The full compatibility verification (torchtune builders, tokenizer, shards) was
  documented at the time and is preserved in the git history (`ml-learning-to-evict/PLAN.md`).

## Result

- The pipeline runs end-to-end with the small model: data generation, per-(layer, head)
  agent training, and evaluation against the heuristic baseline (`RandomPress`).
- PPO with a critic works as a drop-in replacement for the paper's RLOO on the same
  future-attention reward. Comparison curves: `ml-learning-to-evict/learning_curves.png`
  (generated by `scripts/plot_rloo_vs_ppo.py`).
- The goal of this stage was to validate the implementation, not to obtain numbers
  comparable to the paper (RULER truncated to 2048 can cut the needles; the paper trains
  on 8 H100s, we train on one GPU).

## What the report says

The report (§4.2) uses this stage as the starting point: it verifies that the
reproduction of the method is correct and motivates the sequential reformulation. The key
conclusion that triggers the rest of the work: KVP's one-shot ranking (a Plackett-Luce
distribution over permutations) is not expressible in Gymnasium's action spaces, which is
why Apple needs a custom trainer. Our proposal (eviction as a sequence of `Discrete`
decisions with action masking) is what gets built in [01](01-env-first-rewards.md).

## Raw data

- `ml-learning-to-evict/learning_curves.png` (RLOO vs PPO).
- Activations and agent checkpoints are gitignored (`data/`, `agents/`); they are
  regenerated with `./run_experiment.sh`.

## Status

Valid as a pipeline validation. The numeric results on truncated RULER are not comparable
to the paper (by design). The independent reimplementation of the KVP method used as the
reference in the report (passkey ranker) lives in `kv-eviction-gym/scripts/passkey_ranker.py`
and is documented in [12](12-capstone-passkey.md).
